Dataset Limitations & Real-World Considerations

This demo achieves 92.9% validation accuracy on Kvasir-v2, but several factors mean that number should be interpreted cautiously before drawing conclusions about clinical readiness.

! Equipment Color Bias

All Kvasir-v2 images were captured at a single hospital using the same endoscopy equipment. Each class has a consistent color profile — normal cecum images share a yellowish hue, polyp images a reddish tone — that reflects the camera and lighting rather than pathology alone. The model may have learned to key on these color signatures as a shortcut rather than learning the underlying tissue morphology.

In production More aggressive color augmentation during training — random hue shifts, grayscale conversion, histogram equalization — would force the model to learn structure over color. Evaluation on images from multiple hospitals with different equipment is required to confirm generalization.
! Potential Patient Leakage

Kvasir-v2 does not disclose patient counts or how images are distributed across patients. If multiple images from the same patient appear in both the training and validation sets, the model may be partially memorizing patient-specific anatomy — mucosal texture, vascular patterns, and color profiles that are consistent within a patient regardless of class. This would artificially inflate validation accuracy.

In production Datasets must be split by patient ID, not by image. All images from a given patient go entirely into train or entirely into validation — never both. This is standard in clinical ML and is why benchmark accuracy often drops significantly when applied to new patient cohorts.
! Single-Site, Curated Data

Real colonoscopy datasets are heavily imbalanced — polyps appear in roughly 20–30% of procedures, meaning a model trained on real data would see far more normal images than pathological ones. Kvasir-v2's perfectly balanced 1,000-images-per-class distribution is an idealized condition that does not reflect clinical prevalence. A naive model on real data could achieve high accuracy simply by always predicting "normal."

In production Class-weighted loss functions, oversampling of minority classes, and threshold tuning based on the clinical cost of false negatives versus false positives are all required. In cancer screening, missing a polyp (false negative) is far worse than a false alarm (false positive), so decision thresholds should be tuned accordingly.
! Classification vs. Localization

This model outputs a single class label for the entire image — it can tell you a polyp is present but not where. Global average pooling in the EfficientNet head discards all spatial information before the classifier sees it. In a clinical setting, a tool that cannot indicate the location of a finding has limited utility for guiding a physician's instrument.

In production Segmentation models (U-Net, Mask R-CNN) trained on pixel-level annotations like the Kvasir-SEG dataset would produce an overlay mask showing the exact boundary of each polyp. This is the architecture used in research-grade clinical decision support tools.

Engineering & MLOps

Beyond the model itself, this project demonstrates the production practices that turn a trained checkpoint into a maintainable, observable service.

Grad-CAM Explainability

After each prediction, gradient-weighted class activation maps highlight which regions of the image the model attended to. Implemented from scratch using PyTorch forward and backward hooks — no external libraries. Toggle between original and heatmap overlay using the buttons above the preview.

app/inference.py → _GradCAM
Confidence Warnings

Predictions below 60% confidence display a red warning banner; predictions between 60–80% show a yellow caution notice. In a clinical tool, overconfident presentation of a borderline result is a patient safety issue — uncertainty should be surfaced explicitly rather than suppressed.

app/static/app.js → renderResults()
27-Test pytest Suite

Three test modules cover the full stack: transform shape and determinism, inference output structure and Grad-CAM correctness, and all five API endpoints including error paths. A session-scoped fixture builds a random-weight EfficientNet-B0 checkpoint at test startup so tests never require the trained model file.

tests/ → test_transforms, test_inference, test_api
Structured JSON Logging

Every request and prediction is emitted as a single JSON line containing timestamp, level, method, path, status code, and duration. In Cloud Run, the log aggregator can parse these fields directly without regex scraping, enabling metric-based alerts on p99 latency or error rate. A custom JsonFormatter extends the standard library logger — no third-party dependency.

app/logging_config.py → JsonFormatter
GitHub Actions CI

All 27 tests run automatically on every push and pull request via a GitHub Actions workflow. The workflow installs PyTorch's CPU-only wheel (~200 MB) rather than the full CUDA build (~2 GB), keeping CI fast. Python dependency caching means subsequent runs skip reinstalling unchanged packages.

.github/workflows/ci.yml
Input Validation

The /predict endpoint rejects non-image files and empty uploads with a 400 status and a descriptive error message before the payload reaches the model. PIL's Image.open() is used as the validation gate — if the bytes are not a decodable image, the request is rejected immediately rather than causing an opaque server error.
